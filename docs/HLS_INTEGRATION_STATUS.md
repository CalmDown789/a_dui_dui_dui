# 多通道流式 3×3 卷积联合验证

## 数据流

当前联合模块按以下顺序接收输入：

`row → column → input_channel`

也就是同一空间位置的 `Cin` 个 INT8 激活连续进入。模块内部完成：

`每通道两行缓存 → 每通道3×3窗口 → 9路乘法 → 输入通道累加 → INT32输出`

每个完整 3×3 窗口输出一个输出通道的 INT32 卷积结果。

## C 仿真

测试配置：

- 特征图：4×5×2；
- 通道 0：1 至 20 的递增矩阵，3×3 权重全 1；
- 通道 1：像素恒为 2，3×3 权重全 -1；
- 偏置：7；
- 期望输出数量：`(4-2)×(5-2)=6`。

6 个输出均与软件直接计算一致：

`CONV3X3_STREAM_TEST_PASS results=6`

## HLS 综合结果

目标器件：`xc7z020-clg400-1`。自测时钟约束：10 ns。

| 指标 | 结果 |
|---|---:|
| 输入通道循环 II | 1 |
| 估算 Fmax | 140.87 MHz |
| BRAM_18K | 16 / 280 |
| DSP | 6 / 220 |
| FF | 853 / 106400 |
| LUT | 1349 / 53200 |

两行缓存按最大 16 输入通道、640 像素宽度综合。3×3 空间维度并行，输入通道顺序复用算术单元。

## 结论边界

- 目前只计算一个输出通道，尚未加入 8/16/4 输出通道调度。
- 当前只输出完整窗口，不代表最终 padding 已冻结。
- 输出仍是 INT32，尚未套用成员 B 的 requantize 和 PReLU 规则。
- 权重暂由 `ap_memory` 端口提供，最终加载方式和存储组织仍需与成员 A 的系统方案配合。
- 当前报告是 HLS 估算，不是 Vivado 实现后时序，也不是板上帧率。
- 10 ns 只是成员 C 的候选验证条件，不替成员 A 确定最终时钟。
