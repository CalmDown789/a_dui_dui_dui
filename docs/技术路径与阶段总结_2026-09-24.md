# FSRCNN 超分辨率 FPGA 项目技术路径与阶段总结

> 截止：2026-09-24（北京时间）。供小组成员制作 PPT 和答辩时统一口径。本文的“实测”按软件评估、仿真、综合布线、单模块上板、整机上板分别标明；后续判断均为规划，不是验收结果。

## 一页结论

项目已从板卡与网络可行性调研，推进到 ACX750-200T 上的五层 FSRCNN 整数流式架构。A 完成模型训练、量化和逐层向量；B 完成五层 RTL；C 完成板级输入、缓冲、读回以及真实 B+C 集成。在 Vivado/XSim 2022.2、`xelab -O0` 下，960×540 输入到 1920×1080 输出的 **2,073,600 字节与 A 的整数 Golden 全部一致**。真实 B+C 已综合并完整布线，资源为 394 DSP48E1、230 RAMB36 + 8 RAMB18；正式基线在 200 MHz 下 post-route WNS 为 **-2.208 ns**。因此现在可称“算法交付和全帧功能仿真通过、真实硬件实现已得到资源与时序数据”，**不能称“完整网络已上板”或“1080p30 已实现”**。最新实验组合的 WNS 到 -0.738 ns，仍未闭合，且尚未并入正式 RTL。

## 1. 从调研到板卡选择

最初的目标是轻量视频超分，并评估 PYNQ-Z2 上 540p→1080p、30 fps 的可能性。调研先拆开模型 MAC、DSP、片上缓存、DDR 和视频接口：原生较宽 FSRCNN 在小板上缺乏足够余量，末层反卷积必须改成低分辨率域计算的子像素头；中间特征尽可能按行流动，不能把整帧层间张量写回 DDR。小组曾考虑把 PYNQ-Z2 演示收敛到 360p→720p，随后因实际可用板卡和目标发生变化，转向 **ACX750-200T / `xc7a200tfbg484-2`**，恢复 960×540→1920×1080 的目标。

这次换板不是简单扩大 DSP 数。ACX750 是纯 Artix-7，没有 Zynq PS；视频输入、存储调度与显示链路必须由 PL、板上接口或外部主机承担。早期还根据板卡接口资料修正过“无 HDMI”的判断：该板有 HDMI TX 和 DVP 摄像头接口，但没有现成的 HDMI RX 视频输入通路。任务书最终把 ROM 输入、条带缓冲、UART 读回作为可控的阶段性路径，实时视频链路另行验收。以上板卡接口认识属于资料核查；尚无本项目完整视频链路的板测证据。

## 2. 拿到板子后，先把最小硬件假设测清

板卡基线先验证 `xc7a200tfbg484-2`、50 MHz 板载时钟到 200 MHz MMCM、JTAG 下载、DSP48E1 的双整数打包。`bench/onboard_dual_int8/` 留有 bitstream、utilization、post-route timing 和操作手册：单 DSP 工程占 1 个 DSP48E1、162 LUT、227 FF，200 MHz WNS **+0.326 ns**。项目记录称板上 LED 自检完成约 1,677 万组穷举且 0 错；仓库中可直接复核的是构建和时序报告，板上 LED 原始视频/截图未随报告入库。这个结果只支撑**单模块、指定打包格式**在真实芯片上的基线，不能外推为五层网络 200 MHz 或 30 fps。

随后把单 DSP 窗口累加、DSP 级联和共享权重分别做成微基准。K=25 的仿真补跑是 306 例、0 mismatch，并在补跑中定位了两个只在大窗口暴露的位宽/取位错误：DSP48E1 的实际乘法输入是 25×18 位，不能把 30 位 A 端口当成 30 位乘法器；高段解包与偏置补偿必须按真实位宽设计。这些是**微基准仿真**，不是最终 B RTL 已达到“2 个完整 INT8 MAC/DSP”的证明。正式网络中间激活是 INT16，故 `740 × 2 × 200 MHz × 45% = 133.2 GMAC/s` 只能当有条件的理论估计，不能当实测供给。

## 3. 任务书为何一改再改

任务书经过 v2 对口径、v3、v3.1、v3.2、v3.2.1、v3.2.2，多轮修改的核心是让 A 的网络、B 的运算、C 的接口和验收判据**说的是同一个系统**，而非润色文字。

| 阶段 | 发现的问题 | 人工核查和修订结果 |
|---|---|---|
| v2→v3 | 网络通道定义、末层“9×9 权重转换”与 A 实际模型不一致；25 项级联一度把推导写成实测 | 对权重形状、逐层 MAC 和量化文件重新核算，定为 d16/s8/m1/c16、原生稠密 5×5 `Conv 16→4` + PixelShuffle×2；K=25 后续单独补跑 |
| v3→v3.1 | C 的板级责任、P0 功能到 P4 30 fps 的分级验收不够具体 | 加入顶层、ROM、64 行 ping-pong、读回、综合、时序和上板证据要求 |
| v3.1→v3.2 | 把 INT16 激活误写成 INT8 语义；把特定 DSP 打包误推广为最终吞吐；把浮点/QDQ 输出误当整数 RTL Golden | 查 `quant_params.json`、逐层向量与参考算法，分别冻结量化语义、DSP 实现和整数 bit-exact 基准；把 133.2 GMAC/s、3.02× 余量降为待验证理论值 |
| v3.2→v3.2.1 | UART 传输时间、ping-pong 性质、KB/KiB 和指标来源存在歧义 | 修正单位与验收措辞，区分模型效果、RTL 数值和板上吞吐 |
| v3.2.1→v3.2.2 | C-B 流接口缺反压/帧边界；64 行被误当计算 tile；BRAM 行缓存只算单层；存在 80% 与 85% 双上限 | 补 `out_ready`、`stripe_last`、`frame_last` 和 ROM 读契约；明确 64 行是输出缓冲单位；按 11 行整网感受野重算理论缓存，统一 85% 上限并要求以综合报告回填 |

**现行执行文档是 v3.2.2，v4 最终冻结版尚未发布。** v3.2.2 写作时的若干“待完成”状态已被后续代码推进覆盖，汇报当前结果应以本报告下面的实证和相应日志为准，不要把任务书旧状态表当成 9 月 24 日现状。

## 4. 按任务书推进的实际实现

### A：模型、质量与整数合同

模型按 8-bit Y 通道、960×540 输入、1920×1080 输出训练；结构为 Feature 5×5、Shrink 1×1、Mapping 3×3、Expand 1×1、原生 5×5 四通道子像素头。结构核算为 **1.4681088 GMAC/帧**，30 fps 需求为 **44.043264 GMAC/s**。A 完成 50 epoch 固定种子训练，Set5 平均 PSNR：双三次 32.6398 dB、FP32 34.1202 dB、软件量化 34.0190 dB，量化相对 FP32 损失 0.1012 dB；这些是软件图像质量结果，并非 FPGA 输出质量。交付含 INT8 权重、INT16 激活、INT32 累加/偏置、Q1.15 PReLU、四组 96×54 逐层向量及独立的全帧**整数** Golden。逐层哈希和软件参考代码使 B/C 可以从第一处差异定位，而不依赖肉眼看图。

### B：五层 RTL 与可复用流式模块

B 将 5×5/3×3 窗口、固定乘加 lane、后处理、层间 FIFO 和 PixelShuffle row bank 组合为流式五层核，并保留量化 ROM。`IMG_W/IMG_H` 影响行缓存深度和计数，不按像素数复制计算单元；真实综合统计有 354 条卷积乘法 lane，连同后处理共 **394 DSP**。L5 用 200 条卷积 lane，是时序和资源的重点。B 的真实代码与 C 侧局部修复分开保存并记录哈希，便于区分上游交付和集成补丁。

### C：板级输入、握手、缓存、读回及集成

C 将真实 B 置于正式仿真/综合路径，连接 ROM 输入、同步请求响应、2-entry 弹性 FIFO、条带缓存和输出读回，并以 `out_ready` 处理反压。64 行是 C 的输出条带缓冲单位，不等于 B 必须重算的计算 tile。当前 9/9 回归 PASS，包括长背压、四组 96×54 bit-exact 和 960×540 全帧；全帧输入 518,400 字节，输出 2,073,600 字节，mismatch=0、X=0、17 个 stripe_last、1 个 frame_last。该通过仅限冻结的 RTL/ROM/Golden、XSim 2022.2 和 `xelab -O0` 配置。

## 5. 最费人工的排错与验证

1. **把“仿真错”从“RTL 错”中剥离。** 最初 B 自带测试台和 C 集成测试都出现第 3 字节失配。先核 ROM、端序、Golden、握手与参数，再做逐层探针和相同输入/哈希对照，最终定位到 XSim 2022.2 默认 elaboration 优化；`xelab -O0` 后四组和全帧全部逐字节一致。还检查了 B 原测试台同沿阻塞赋值引入的事件排序竞争，正式判据采用稳定驱动的 C 测试台。这里投入的是设计实验、锁定变量、逐层分析，不是简单改一个仿真开关。
2. **解决 Vivado 综合内存异常。** 原 RTL 用运行时相位选择宽 packed bus 的动态切片，真实五层综合在 RTL Optimization Phase 2 涨至约 30.4 GB 且没有生成报告。对单层隔离、比较数组维度和索引写法后，将相位选择改成 elaboration 可见的静态 `case`；相同规模 B+C 全流程峰值降至约 3.13 GB（综合）/4.13 GB（实现），并得到可审计的层级资源表。
3. **以真实 post-route 数据反复筛选时序方案。** 正式基线 WNS -2.208 ns。单加 MAC 寄存器被综合吸收，反而到 -2.370 ns；AggressiveFanoutOpt + Explore 到 -1.949 ns，但 route 时间显著增加；复制每个输出 lane 的 phase 状态到 -2.975 ns，LUT 增约 26.7%，已撤销；L5 高扇出约束到 -2.057 ns，但关键路径转到窗口数据→DSP；150 MHz 仍失败，120 MHz 仅 +0.012 ns，缺乏板测裕量。后续组合实验把 FIFO 宽字分片，在匹配的临时基线上从 -1.097 改为 -0.738 ns，仍未过 200 MHz。36-bit accumulator 变体只完成探针、smoke 和综合，未 route。每项都以匹配基线、真实布线结果和失败撤销记录为准。
4. **人工对齐文档、代码和证据。** 任务书多轮纠错、整数 Golden 与 QDQ 分离、源文件闭包与哈希、资源层级自检，以及对“单 DSP 上板”和“完整五层未上板”的严格区分，避免小组成员各拿一个数字做 PPT，最后互相冲突。

| 单 DSP 板卡基线 | 有 bitstream、200 MHz 正 slack 和板上自检记录；缺板上原始采集附件 | “单模块板测基线完成” |
| 五层数值正确性 | XSim 2022.2 `-O0` 四组及全帧 Golden 对拍 PASS | “全帧整数功能仿真通过” |

下一阶段先在独立 Vivado 2022.2 runner 上复现并筛选 L5 路径优化，给 UART 引脚、启动和输出链路补约束；**只有目标时钟和板级约束过关后**，生成完整 bitstream，在同一 ACX750 上采集输出，与同版整数 Golden 逐字节比较，再测帧率和画质。不能把模拟时钟周期、模型理论 GMAC 或单 DSP 的 WNS 当作整机帧率。

## 7. 同一块 ACX750 做 1080p→4K：判断与 AI 代码重构顺序

这里的 4K 指 **1920×1080 输入、×2 得 3840×2160 输出**，沿用当前五层模型结构时输入像素数是当前的 4 倍。因此模型计算至少变成 **5.8724352 GMAC/帧**，4K30 要 **176.173056 GMAC/s**；输出为 8,294,400 字节/帧，30 fps 的纯 Y 数据流约 **248.832 MB/s**，还未计输入、协议、存储与显示开销。即使采用尚未在最终网络验证的 133.2 GMAC/s 理论供给，4K30 的计算需求也已超过它；正式五层当前连 200 MHz 时序都未闭合。因此同板上 **4K 静态图/低帧率演示可作为研究方向，4K30 不能在现有架构上承诺**。4K 视频输出还取决于接口、像素时钟和接收设备，现有 UART 读回只适合调试/离线采集。

按风险和收益排序，下一轮应重构以下由 AI 辅助生成并已暴露参数化/物理实现问题的代码。每项先固定当前 1080p Golden 回归，再做 4K 参数测试，最后以真实综合、route 与板上采集决定是否保留。

| 优先级 | 代码位置/模块 | 重构动作与验证门槛 |
|---|---|---|
| P0 | B `phase_mac_pipeline.sv`、`mac_issue_stage.sv`、L5 `fsrcnn_stream_layer.sv` | 消除运行时宽向量动态切片，显式分层相位选择；按 DSP 邻近关系分组 lane 和权重/窗口数据，限制 phase 与数据高扇出；逐层 bit-exact、综合内存和 post-route WNS 都要测，不再用综合 slack 代替 route |
| P0 | C `input_rom.v`、`input_stream.v`、`c_core.v`，B 行窗口与 PixelShuffle row banks | 把 960/1920 固定宽度和单一 ROM 图源抽成行宽/步长/帧界参数；4K 输入不能照搬整帧片上 ROM，改成外部流/DDR 分块和有界行缓存；证明条带跨界 halo、背压、帧末与 bank 地址均正确 |
| P1 | B `phase_accumulator.sv`、`prelu_requantize.sv`、L5 宽 FIFO | 用严格位宽证明替代过宽中间数组；36-bit 候选须完整 route + 全帧整数对拍，宽 FIFO 分片须和同一代码基线比较；保留端到端 INT32/饱和/舍入语义 |
| P1 | A `model.py`、`quantization.py`、`fixed_reference.py`、`pipeline.py` | 把网络结构、输入几何、权重量化、整数算子和验收向量拆成明确配置与版本合同；训练 4K 输入对应的质量模型或蒸馏更轻的模型，重新评估 PSNR/SSIM 与 MAC；Golden 支持分块/流式生成，避免 4K 全层中间数组耗尽内存 |
| P1 | C `scripts/run_sim.tcl`、`synth_bc_real.tcl`、测试台 | 统一参数来源、RTL/ROM/Golden 哈希、工具选项和结果清单；测试台在非采样沿驱动，增加长行、条带边界和连续帧场景；自动比较 1080p 与 4K 的 per-layer 资源、WNS、BRAM 与每输出像素周期 |
| P2 | C 输出读回/视频接口 | UART 留作控制与低速证据通道；为 4K 帧输出评估板载高速接口或外部采集，并用实际链路带宽、时钟和协议实测验收；不能把“算出 4K 像素”当作“4K 视频显示” |

工程决策应分三级：先在原板**闭合并上板验证 1080p**；再做**4K 单帧 bit-exact 与资源/时序试验**；最后只有当实测吞吐和输出链路都达到目标，才提出 4K fps 指标。如果结构不变的 4K30 算力下界仍超预算，应优先换更轻的网络、降低帧率或增加外部计算资源，而不是靠调 Vivado 指令宣称可达。

## 8. PPT 统一用语与证据入口

建议各成员的 PPT 使用同一条主线：“**调研算力/板卡 → 单 DSP 板测 → 多版任务书纠错冻结 → A 模型和整数合同 → B 五层 RTL → C 板级集成 → 全帧 Golden 仿真 → 真实布线暴露时序瓶颈 → 1080p 板测与 4K 重构路线**”。第一页放本报告的一页结论；技术页每个数字标“软件/仿真/综合/布线/板测”。`44.043264 GMAC/s` 是需求，`133.2 GMAC/s` 是有条件理论估计，`-2.208 ns` 是正式 200 MHz route 结果，`-0.738 ns` 是组合实验结果，不能混写。
