# BRAM 预算对齐表 —— 「192 块」到底是什么，怎么和 B 的 271 对上

> 用户指令 §四：把 B 报的「192 blocks measured」与系统存储预算对齐，
> 说清 192 的含义、来源/证据、映射到特征图/FIFO/缓存/权重各占多少；
> **不得**把「单模块 / 单次综合」的结果写成整个系统的结论。

---

## 1 先纠正一个口径错误：「192」不是 B 报的，也不是系统总量

| 说法 | 是否成立 | 说明 |
|---|---|---|
| 「192 blocks **是 B 测的**」 | ❌ 不成立 | 192 出自 **C 侧骨架** 的 Vivado 综合报告，与 B 无关 |
| 「192 blocks **是系统总 BRAM**」 | ❌ 不成立 | 192 只含**已经实现**的两块存储；B 侧的 44 块尚未落进综合 |
| 「192 blocks **是 C 骨架 synthesis-only 的 RAMB36 占用**」 | ✅ 成立 | 见下 §2 证据 |

来源证据（可直接复现）：

- `report/utilization_synth.rpt` —— `Block RAM Tile 192 / 365 (52.60)`、`RAMB36/FIFO 192`、`RAMB18 0`
- `report/synth_result.txt` —— `Design State : Synthesized`、`implementation : **未执行**`
- 生成脚本 `scripts/synth_check.tcl`，part `xc7a200tfbg484-2`，top `c_synth_top`

⚠️ 三个必须同时声明的前提，否则这个数字会被误用：

1. **synthesis-only**：未做 place/route，不是实现后数字；
2. **top = `c_synth_top`**：C 侧骨架，**未实例化真实 B**（`b_core_stub` 为占位）；
3. **commit 相关**：数字随 commit 变化，引用时必须带 commit SHA（§5）。

## 2 「192」的逐项拆解（有综合报告逐行支撑）

Vivado 的 `Block RAM: **Final** Mapping Report`（`_syn` 抓取，见 `_syn/rammap.txt`）
只列出两个 RTL 对象，且注明「Multiple instantiated Block RAMs are reported only once」：

| # | 层次对象 | 形状 | 实例数 | RAMB18 | RAMB36 | 小计 |
|---|---|---|---:|---:|---:|---:|
| 1 | `u_top/u_core/u_rom`（`input_rom.v`） | 120 K x 8 → **512 KiB 输入 ROM** | 1 | 0 | 128 | **128** |
| 2 | `u_top/u_core/u_pp/u_bank0/mem_reg` | 120 K x 8（ping-pong A） | 1 | 0 | 32 | **32** |
| 3 | `u_top/u_core/u_pp/u_bank1/mem_reg` | 120 K x 8（ping-pong B） | 1 | 0 | 32 | **32** |
| | | | | **0** | **192** | **192** |

**128 + 32 + 32 = 192**，与 `report_utilization` 的 192 完全对上。

逐项按容量核对（1 RAMB36 = 36 Kbit = 4.5 KiB）：

| 项 | 逻辑容量 | 最小 RAMB36 | 实际占用 | 浪费 |
|---|---:|---:|---:|---:|
| 输入 ROM 524288 × 8 bit | 512.00 KiB | 4 Mbit / 36 Kbit = 113.8 → 114 | **128**（512 K 深 > 32 K 深，需 16 级级联 × 8 bit 宽） | 64 KiB |
| ping-pong 2 × 122880 × 8 bit | 2 × 120 KiB = 240.00 KiB | 1.92 Mbit / 36 Kbit = 53.3 → 54 | **64**（每块 122880 深 → 4 级级联 × 8 bit） | 48 KiB |
| **合计** | **752.00 KiB** | 168 | **192** | **112 KiB** |

结论：192 里 **112 KiB（约 14.9% 的 BRAM 位）是深度级联造成的结构性浪费**，
这是「512 K 深单端口 ROM」在 32 K 深 BRAM 上的必然代价，不是设计缺陷。

### 2.1 一个必须记下来的负面证据

综合日志里有这条：

```text
WARNING: [Synth 8-4767] Trying to implement RAM 'rowbuf_reg' in registers.
         Block RAM or DRAM implementation is not possible; see log for reasons.
RAM "rowbuf_reg" dissolved into registers
```

`rowbuf_reg` 来自 **`b_core_stub`（占位）**，读出的行缓冲**没有占用任何 BRAM**，
而是散成了寄存器。⇒ 今天这 192 块里 **一块 B 的行缓冲都没有**。
真 B 接进来之后，B 的行缓存必然新增 BRAM（见 §3）。

## 3 与 B v1.1 的 271 块对齐

B 的口径（`成员B对C架构接口与资源预算确认_v1.1.docx` §5 表 7）逐项照抄：

| # | 项 | B v1.1 报 | 归属 | C 综合实测 | 差异 | 差异原因 |
|---|---|---:|---|---:|---:|---|
| 1 | 输入图像 ROM | **127** | **C 侧** | **128** | **+1** | 同一块存储；B 按 127 估算，C 实测 128（512 K 深需 16 级级联 × 8 bit 宽） |
| 2 | 64 行双缓冲 | **60** | **C 侧** | **64** | **+4** | 同一块存储；B 估 30×2，C 实测 32×2（见 §3.2） |
| 3 | L1/L3/L5 行缓存 | 42 | B 侧 | 0 | −42 | 真实 B 未接入（stub 行缓冲散成寄存器，§2.1） |
| 4 | 相位行双 bank | 2 | B 侧 | 0 | −2 | 同上 |
| 5 | 参数（权重/bias/PReLU/Q31） | **0** | B 侧 | 0 | 0 | **一致**：v1.1 走 M3「bank 化 LUTROM / 寄存器」，3.27 KiB **不占 BRAM** |
| 6 | 系统预留（ILA/UART/控制/碎片） | 40 | C 侧 | 0 | −40 | C 尚未实现预留区 |
| | **合计** | **271** | | **192** | **−79** | |

> 🛠 **2026-09-23 修正（本文件初版的错误，必须记下来）**：
> 本文件初版把 B v1.1 的「127」误标为「**B 侧参数 ROM**」，并据此在 §3.1 外推出
> 「403 块、超出 93 块、预算显著不闭合」的结论 —— **该结论作废**。
> 对照 v1.1 §五 表 7：**127 = C 输入 ROM**，而**参数一项 B 自己写的是 0**
> （v1.1 §五 M3 明确「权重、bias、PReLU、Q31 裸参数仅 3.27 KiB，不占 BRAM」）。
> 误把 127 当成一块**并不存在**的 B 侧参数 ROM，等于凭空多算了 127 块。
> 教训：**B 的表 7 是「项 → 块数」的完整清单，逐项照抄，不得按记忆改名归属。**

**不得相加的两块 ROM（易错点仍保留，只是归属要写对）**：

| 存储 | 归属 | 内容 | 块数 | 状态 |
|---|---|---|---:|---|
| 输入图像 ROM `input_rom` | **C 侧** | 960×540 单帧 Y（512 KiB，含 5888 B 零填充） | **128**（B 估 127） | ✅ 已实现（综合实证） |
| 参数（权重/bias/PReLU/Q31） | **B 侧** | 合计 3344 B | **0 块**（放 LUTROM / 寄存器） | ⛔ 未实现；**本就规划为不占 BRAM** |

### 3.1 系统预算闭合（外推，非实测）

按「C 已实测值 + B v1.1 未实现项 + v1.1 系统预留」外推：

```
C 已实测   输入ROM 128 + ping-pong 64                          = 192
B v1.1 待实现              行缓存 42 + 相位 bank 2              =  44
B 参数（v1.1: LUTROM/寄存器，不占 BRAM）                          =   0
系统预留（按 v1.1）                                              =  40
---------------------------------------------------------------------
外推合计                                                          276 RAMB36
```

换算与对照：

| 口径 | 数值 | 结论 |
|---|---:|---|
| 外推合计（物理 RAMB36） | **276 / 365 = 75.62%** | — |
| 折合物理容量 | 276 × 4.5 KiB = **1242.0 KiB** | — |
| B v1.1 自身理论值 | 271 / 365 = 74.25% = **1219.5 KiB** | B 的原口径（用 B 自己的 127/60 估算） |
| **85% 预算线**（全文统一上限） | 365 × 0.85 = 310.25 → **310 块 = 1395.0 KiB** | — |
| **余量** | 310 − 276 = **34 块 ≈ 153.0 KiB** | ✅ **外推在 85% 线内** |
| 任务书 v3.2.2 §五.13 **口径②**（旧字节口径） | ≈ **1406.6 KiB** | ❌ 超 85% 线 ≈ 10.5 KiB（**未闭合**） |

**⇒ 结论按两级表述，且必须同时写出「按哪一套口径」：**

- **一级（理论/规划口径）**：
  - 按**任务书 v3.2.2 §五.13 口径②**（字节累加）⇒ ≈1406.6 KiB > 1396.1 KiB，**未闭合**；
  - 按 **B v1.1 §五 物理 RAMB36 口径**（按 RAMB36 宽深比向上取整后分项列示）⇒
    理论 1219.5 KiB、**用 C 实测值替换 B 估算后 1242.0 KiB**，**均在 85% 线内，闭合**；
  - 两口径**互不否定**：差异来自「按有效字节算」还是「按物理块向上取整算」、
    以及是否把 40 块系统预留计入。B v1.1 §五 已原文明示其口径
    「相对 C 所报 1406.6 KiB 旧口径……减少约 187.1 KiB……低于 85% 预算 1396.1 KiB 约 176.6 KiB」，
    并附条件「最终数值以 C 侧 Vivado 综合利用率报告为准」「若 C 侧 ILA 或其他 IP 超过
    40 块 RAMB36 预留，双方按综合报告重新压缩」。
- **二级（实测口径）**：**仍未闭合**。今天只有 **C 侧骨架 192 块**是实测量；
  项目 3/4（B 行缓存 42 + 相位 2）与项目 6（预留 40）**全是规划值**，
  真实 B 未进综合。故**不得**写「BRAM 已闭合」，只能写
  「**按 B v1.1 物理块口径外推在 85% 线内（余量 ≈34 块），二级实测待 B 接入后综合复核**」。

> ★ 免责：§3.1 是**外推**。B 的行缓存/相位 bank 一天没落进 RTL，
> 那 44 块一天就是**规划值**；40 块预留同理。任何「系统 BRAM 已实测闭合」的说法都无证据。

### 3.2 为什么 C 实测 64 块而 B 估 60 块（两个口径都对）

B v1.1 §1 表 1 的推导与 C 实测**方法一致、取整位置不同**：

| 项 | B v1.1 的算法 | 结果 |
|---|---|---|
| 单 bank 有效数据 | 1920 × 64 × 8 bit | 983040 bit = 122880 B |
| 纯容量下限 | 983040 / 36864 | 26.67 RAMB36 |
| 8/9-bit 模式 | ceil(122880 / 4096) | 30 RAMB36/bank |
| 64/72-bit 模式 | 15360 × 64-bit word；ceil(15360 / 512) | 30 RAMB36/bank |
| 双 bank | 2 × 30 | **60 RAMB36 = 270 KiB** |

C 侧实测 **32/bank**（合计 64）而不是 30/bank：Vivado 对 `122880 深 × 8 bit`
的推断结果是**每块 4 级级联**（122880 / 32768 = 3.75 → 4），
而 B 的 30 来自「按 4096 深 × 9 bit 宽」的分割假设。**两者都是向上取整，
只是把取整放在了不同的维度上**。B v1.1 已把这点写进 §1：
「60 个 RAMB36 预算是 RAMB36 端口宽度/深度组合造成的物理向上取整，
不是随意增加的保守量……最终仍以 C 侧综合报告确认推断结果」。
⇒ C 的 64 就是那句「以 C 侧综合报告确认」的**答案**，差异 **+4 块 = +18 KiB**。

## 4 备用余量的来源（未做，仅记录；**不是必需的救命措施**）

按 §3.1，外推已在 85% 线内、余量 ≈34 块。下表是**若 B 接入后实测超线**时的候选手段，
**当前一条都不需要做、也一条都没做**，全部属「理论可省」：

| 方向 | 理论可省 | 代价 | 证据状态 |
|---|---:|---|---|
| 输入 ROM 深度割到 524288 的下界（113.8 → 114 块） | ~14 块 | 需自定义级联（非 2 的幂寻址） | 未实现 |
| 复用输入 ROM 空间承载 ping-pong（存算交替） | ~64 块 | 破坏「ROM 只读」语义 | 未实现 |
| 条带高度 64 → 32（M1 方案） | 取决于 B 行缓存实现 | 五项重算 + B/C 双向确认 | 未实现 |

> ⚠️ 初版此处列过一条「参数 ROM 用分布式 RAM ⇒ 省 127 块」—— **该条已删除**，
> 因为 v1.1 §五 M3 表明参数本来就**不占 BRAM**（0 块），不存在可省空间（见 §3 修正说明）。
>
> ⚠️ 若真要动用余量，`input_rom` 一项的下界是 **114 块**（纯容量），
> 而实测 128 块里有 14 块纯属深度级联浪费 —— 这是唯一「有实测支撑」的可省项。

## 5 引用规范（写给后续写文档的人）

写 BRAM 数字时必须同时给出这五项，缺一不可：

1. **口径**：`synthesis-only` 还是 `post-route`；
2. **top**：`c_synth_top` / `b_real_bench_top` / 其他；
3. **是否含真实 B**：含 / 不含（含哪一部分）；
4. **part**：`xc7a200tfbg484-2`；
5. **commit SHA** + 报告文件路径。

**禁止**：把 `b_real_bench_top`（B 原语集合）的数字写成系统数字；
把 synthesis-only 的 WNS 写成 Fmax；把 B 的规划值写成实测值。
