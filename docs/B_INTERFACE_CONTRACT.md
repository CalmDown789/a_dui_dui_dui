## 一、结论先行：IMGW / IMGH / STRIPEH 到底怎么传

**答：B v1.1 的 C-B 接口里不存在这三个信号，也不存在任何尺寸总线。**

| 问题 | 结论 | 依据 |
|---|---|---|
| **传递方式** | **不通过端口传递。** B v1.1 §九「C-B v0.2 冻结矩阵」把 `输入960×540 uint8 Y`、`输出1920×1080 uint8 Y`、`64行条带边界，最后条带56行` 三项列为**已冻结**常量 | v1.1 §九 表 10 |
| **位宽** | **不适用** —— 端口表（§六 表 8）共 13 个信号，全部是 1 bit 或 8 bit（`in_data` / `out_data`），**没有任何几何尺寸域** | v1.1 §六 表 8 |
| **时序** | 尺寸量在**编译期（elaboration）**生效，**不存在运行时尺寸握手**。运行时的坐标推进只由 `in_valid && in_ready`（输入侧）与 `out_valid && out_ready`（输出侧）驱动 | v1.1 §六「输入推进约束」 |
| **生效时机** | 冻结于设计基线；`start` 接受后 B 直接按固定几何运行，不等待任何尺寸配置 | v1.1 §六 / §九 |

### C 侧当前实现的定位

`rtl/b_core_if.v` 暴露了 5 个 parameter：

```verilog
parameter integer IMG_W = `C_IMG_W,  IMG_H = `C_IMG_H,
                  OUT_W = `C_OUT_W, OUT_H = `C_OUT_H,
                  STRIPE_H = `C_STRIPE_H, DATA_W = `C_PIXEL_W
```

**这些都是 C 侧内部的编译期量，用途仅限**：

1. 在 C 侧生成 ROM 地址、条带计数、末条带行数；
2. 让小规模 testbench 能例化 `b_core_if`（如 32×16→64×32、`STRIPE_H=5`）。

**不得假设**真实 B 模块会读取或响应这些 parameter —— B v1.1 的端口里没有对应入口。
换言之：**C 侧的 parameter 化是 C 的内部便利，不是双方契约的一部分。**

## 二、端口清单（B v1.1 §六 表 8，逐条照抄）

| 信号 | 方向 | bit | 语义 |
|---|---|---:|---|
| `clk_200` | C→B | 1 | 唯一时钟域；150 MHz 降频时**名称可保持不变**，频率由 C 记录 |
| `rst_n` | C→B | 1 | 低有效，含 MMCM `locked` 门控；**B 内部同步释放** |
| `start` | C→B | 1 | **仅在 `busy=0` 时被接受**；首输入最早**下一拍**握手；`busy` 期间 `start` 忽略 |
| `busy` | B→C | 1 | 从 `start` 接受到**最终输出像素握手完成**期间为 1 |
| `done` | B→C | 1 | 最终像素 `out_valid&&out_ready&&frame_last` 的**下一拍脉冲** |
| `in_valid` | C→B | 1 | 输入像素有效；**一旦拉高而未握手，必须保持为 1** |
| `in_ready` | B→C | 1 | B 能接收输入像素；`start` 接受前为 0，**最早下一拍可拉高** |
| `in_data` | C→B | **8** | uint8 Y；行优先；stall 时与当前 ROM 地址、x/y 计数一起保持 |
| `out_valid` | B→C | 1 | 当前输出像素及 sideband 有效 |
| `out_ready` | C→B | 1 | C 能接受当前输出像素 |
| `out_data` | B→C | **8** | uint8 Y，**等价于 `pixel_data`** |
| `stripe_last` | B→C | 1 | 当前像素是本 **64 行条带**的最后一个像素 |
| `frame_last` | B→C | 1 | 当前像素是**整帧最后一个**像素 |

**命名约束（v1.1 原文）**：`pixel_data` / `pixel_valid` **不再作为第二套独立信号**；
若 C 顶层已有这两个名字，可分别**直接连接** `out_data` / `out_valid`。
`out_data` **固定 8 bit**，**不输出 4 相位打包总线**，**不输出 INT16 中间激活**。

## 三、关键时序约定（v1.1 §六 / §七 / §八）

### 3.1 启动与握手

```
定义：start_accept = start && !busy
      input_fire   = in_valid && in_ready
      output_fire  = out_valid && out_ready
```

1. `start` **只在 `busy=0` 时被接受**；被接受后 B 进入 `busy` 并初始化帧状态。
2. **最早从下一拍**开始允许第一颗输入像素握手。
   **不要求、也不接受** `start` 与第一像素同拍。
3. `busy=1` 期间的 `start`：**不重启、不清状态**。
4. **输入推进约束**：C 侧 ROM 地址、输入像素计数器、x/y 坐标
   **只能在 `input_fire` 为 1 的时钟沿加一**；
   `in_valid && !in_ready` 期间**不得预取到下一地址并改变 `in_data`**。
5. `in_valid=1 && in_ready=0` 时，C **必须保持** `in_valid`、`in_data`、
   当前 ROM 地址、输入 x/y 计数器不变；只有 `input_fire` 成立的那一拍才消费一次像素。

### 3.2 输出与 sideband 保持

1. **`out_valid` 不保证整帧连续。** C **只按 `out_valid && out_ready` 计数**，
   **不得依赖固定拍间隔**。
2. 一旦 `out_valid=1` 而 `out_ready=0`：`out_valid`、`out_data`、`stripe_last`、
   `frame_last` **必须保持原值**，坐标与所有输出计数器**不得前进**，直到握手成功。
3. `stripe_last` 在 **`x_out=1919` 且 `y_out ∈ {63,127,…,1023,1079}`** 时置 1；
   **最后条带为 56 行**。
4. `frame_last` 仅在 **`x_out=1919` 且 `y_out=1079`** 时置 1。
5. 二者**只随最后像素握手被消费**。

### 3.3 输出节拍上界（v1.1 §七.3）

- L1~L5 理论上**每 8 拍**完成一个低分辨率空间位置；L5 每个位置产生 **4 个相位字节**。
- PixelShuffle 一个低分辨率行完成后，输出**两个 1920 像素行 = 3840 个连续有效 beat**。
- 在 200 MHz、`ready` 恒为 1 的稳态预算中，**相邻行对之间最多约 3840 个 `out_valid=0` 周期**。
- 首帧首像素还含行缓存预热与流水延迟，**不纳入该稳态上限**。

### 3.4 反压契约 —— **合同级保证 N = 0**

v1.1 §八 原文要点：

- **接口契约不承诺** `out_ready` 拉低后仍可额外接收固定 N 拍。
- 标准 ready/valid 语义下，C 可在**任意拍**撤销 `ready`，B 从该拍起保持当前 beat。
- 由于撤销时内部占用未知，**合同级保证 N=0**；
  物理剩余容量 = 当时空闲 entry 数（相位行双 bank 最多 7680 像素
  ≈ **15360 个核心时钟**的物理吸收空间，但那是**物理余量，不是契约**）。
- **buffer 满后不丢弃、不覆盖、不回绕**：停止相位写入，逐级拉低 `ready`
  或关闭本级 clock-enable，最终使 `in_ready=0`；`out_ready` 恢复后**从原状态继续**。
- **允许无限期停顿**（复位除外）。

> 📌 **对 C 侧的直接影响**：`c_config.vh` 里原本写着
> 「B-ARCH-10 的『最大连续 back-pressure 周期 N』尚未给出」——
> **v1.1 已给出答案：N=0（合同级）**。C 侧不得按「B 能吸收 N 拍」设计缓存深度。
