## 25 帧画质结果

评测只对亮度 Y 计算，峰值 255，SSIM 使用 11×11 高斯窗、sigma=1.5。表中“中心裁边 8”与“全图”分别统计，不混成同一数值。配对 HR 是 UVG 有损 4K HEVC 解码 Y 帧，LR 由同帧以 FFmpeg bicubic ×4 合成；结果描述这套软件退化协议，不等同相机原生 540p 输入的真实画质。

| 输出 / 口径 | PSNR (dB) | SSIM |
|---|---:|---:|
| 直接 bicubic ×4，中心裁边 8 | 41.2766 | 0.974353 |
| 冻结 R0 FP32，中心裁边 8 | 43.4420 | 0.979642 |
| 冻结 R0 整数，中心裁边 8 | 43.1538 | 0.977871 |
| 直接 bicubic ×4，全图 | 41.2796 | 0.974400 |
| 冻结 R0 FP32，全图 | 43.4357 | 0.979651 |
| 冻结 R0 整数，全图 | 43.1399 | 0.977848 |

中心裁边口径下，整数 R0 在这 25 帧均高于 bicubic，平均增加 1.8772 dB PSNR、0.003518 SSIM；逐序列的 PSNR 增量分别为 Bosphorus +1.5715 dB、ReadySetGo +2.2123 dB、ShakeNDry +1.8183 dB。整数 R0 相对 FP32 平均低 0.2882 dB、0.001771 SSIM，25 帧均低于 FP32。该差异反映当前正式定点与 FP32 的软件结果，不证明板端会有同样偏差。

视觉样例按每个序列中整数相对 bicubic 的最小 PSNR 增益选帧；裁切窗口取该帧整数输出对解码 4K 参考的局部绝对误差和最大位置。样例用于检查细节差异，不将模型宣称为逐内容普遍更优。`quality_examples.json` 保留选择依据和坐标；PNG 对照图仅生成在本机 `.data/member_a_task_20261008/visual_examples/`，不随 Git 发布。

## PC 后处理接口

冻结的软件插值规则：Keys cubic `a=-0.5`；半像素中心坐标；边缘复制；可分离 float64 累加；最近舍入、中点远离零；最后饱和到 uint8。输入、输出均为单通道逐行 Y8，输出行优先，不包含文件头、色度或显示缓冲填充。

独立接口可在接收到一帧 1080p 原始 Y8 后调用。命令验证输入恰好 2,073,600 B，防止尺寸或通道错误；输出哈希和 PC monotonic 起止时间写入 JSON。计时只围绕本机插值函数，不是从摄像头/网口接收到显示器呈现的端到端延迟。C 集成时应沿用相同帧 ID，并由 C 在其输入/接收/预览队列另记系统时间。

本机生成并校验的三帧派生 4K 整数参考各 8,294,400 B；对应 SHA/CRC 清单随仓库发布：

| 序列 / 帧 | CRC32 | SHA-256 |
|---|---|---|
| Bosphorus frame 000 | `251042c9` | `4809773e52a8b23595f0232b6d7e36073ed609e33432495fe0490f57c4c9aeed` |
| ReadySetGo frame 000 | `e33f4419` | `72e86b982b5c674625b5972dcee55035b65ea4b7adaa3dfc9a36499161b762d6` |
| ShakeNDry frame 000 | `1940c13c` | `b04dac4745d7138b070e44195cb1e0ef91fc514e924b28ea9b1ff0fd224d9c8b` |

三帧分别对应清单里的 960×540 LR 输入 SHA，供 C 收到同帧 1080p Y 输出后验证插值阶段。指标及哈希清单位于 [`artifacts/member_a_4k_postprocess_golden/`](../artifacts/member_a_4k_postprocess_golden/)；完整像素文件不在 Git 包中，需用下方复现命令生成到忽略目录 `.data/`。

## 软件计时结果

设备：Windows 11、PyTorch 2.11.0+cu128、NVIDIA GeForce RTX 5060 Laptop GPU。固定 Bosphorus `frame_000`，1 次预热、5 次计时；FP32 CPU/GPU 使用同一 checkpoint，均含 540p 输入张量生成、设备间复制和 CPU 1080p→4K 后处理。文件读写、视频解码、网络发送、板端等待、预览队列和显示均未计入。

| 软件路径 | 中位数 | p90 | 单帧倒数（仅供参考） |
|---|---:|---:|---:|
| FP32 CPU：CNN + 4K 后处理 | 446.0 ms | 455.5 ms | 2.24 fps |
| FP32 CUDA：CNN + 4K 后处理 | 379.8 ms | 389.6 ms | 2.63 fps |
| 正式整数 CPU 参考：网络 + 4K 后处理 | 1,914.2 ms | 1,995.0 ms | 0.52 fps |
| 直接 bicubic ×4 CPU | 256.2 ms | 269.8 ms | 3.90 fps |

FP32 CPU 与 CUDA 的 4K 输出在 8,294,400 像素中有 301,557 个像素不同，平均差 0.0364 灰度级，最大差 2；来源是浮点运算顺序差异。上表的单帧倒数不能当作稳态视频吞吐，也不代表 ACX750 性能。当前 CPU 整数参考为可读性优先的逐层精确实现，并非优化过的 PC 推理内核。

## 8K 扩展初步结果

4K 主线稳定后，补测了原生 8K BodeMuseum SDR 序列的第 120、240、360、480 帧。R0 整数分级路径为 `540p → FSRCNN×2 → 1080p → Keys×2 → 4K → Keys×2 → 8K`；直接基线为 Keys ×8。四帧 shave-16 平均 PSNR/SSIM：整数分级 28.2227 dB / 0.826757，直接 bicubic ×8 为 27.5765 dB / 0.818702；差值 +0.6462 dB / +0.008054。R0 FP32 分级为 28.2358 dB / 0.828335。完整方法、逐帧表、计时和复现命令见[成员 A 8K 扩展评估](成员A_8K扩展评估_20261008.md)。

此结果只描述四帧与固定合成降采样协议，不代表内容泛化、连续视频稳定性或 8K 实时能力。HHI 数据采用 CC BY-NC-ND 4.0；源平面和派生图像不进入仓库。A 本人独立讲解/复跑核对表见[成员 A 答辩与自测核对表](成员A答辩与自测核对表_20261008.md)。

## 历史 C 板端回传复核

C 分支 `d6b13e6` 的历史冻结基线附件包含 100/150 MHz 两档共 32 帧原始采集。A 侧按附件实际输入用正式 `FixedReference` 重算四种不同输入，所有板端回传均逐字节零差；帧 0 与 A 全尺寸 Golden 输入/输出哈希一致。此核对不代表新 BIT 或 25 组自然视频的板端 PSNR/SSIM。方法、数据 SHA 和复现入口见[历史板测回传复核](成员A历史板测回传数值复核_20261008.md)。

## A05 优化建议

| 方案 | 现有实验结果 | 建议 |
|---|---|---|
| 正式 R0 | 当前硬件冻结规格；本次 25 帧整数平均为 43.1538 dB / 0.977871（中心裁边 8） | 保留为 B/C 主线基准和首要验收 Golden。 |
| 同结构 QAT seed456 | 另一份 10 段、1,240 帧软件整数实验相对 R0 +0.1034 dB / +0.001088；该实验仍是独立候选 | 可由 B 对候选包做位精确仿真，再决定是否安排新版本；在验收前不替换 R0 ROM。 |
| R1 3×3 子像素头 | MAC 减少 36.2%；25 帧对照相对 R0T 低 0.267 dB / 0.00092 SSIM | 仅在团队确认可接受画质折损且 B 提供资源实测后另立候选。 |
| 隐藏激活 INT8 | 5 个 PTQ 配置及 2 个 QAT 复测未达到 ≤0.10 dB 损失门槛 | 保持 INT16 隐藏激活。 |
| DIV2K QAT/EMA | 100 张评估增益 0.0664 dB，但 checkpoint 仍在本地忽略目录，未正式发布 | 先完成可复现打包和整数候选验收，再纳入讨论。 |

本轮没有改正式结构、权重、量化格式或 Golden；没有由 A 推断 DSP、BRAM、时序或板级吞吐收益。

## 移交与剩余验收

- B：以三个 `frame_000` 输入哈希定位对应数据，确认冻结 R0 的 1080p 整数输出仍与正式 A Golden 一致；模型候选需使用独立版本和独立 Golden。
- C：把接收的 1920×1080 Y8 帧交给 `process_1080_frame` 或命令行入口，核对输出 8,294,400 B、帧 ID、SHA-256 与时间记录；主机预览和整机计时由 C 的链路记录。
- A：收到 C 的同帧原始回传后，用对应输入 ID 对照 1080p/4K Golden，并按相同解码/裁边规则更新板端画质表。

完成以上软件交付不代表整机 4K30、真实摄像头画质或板端预览已经通过；对应验收需要实际板卡输入、回传和持续运行记录。
