# 成员 A 多帧数据交接

交付范围：两幅不同画面的上板检查数据、固定 8 帧预录序列的整数 Golden、电脑端回传比对工具及离线播放器。沿用已冻结的 `d16/s8/m1/c16` 模型和量化参数，不修改 B/C 的 RTL、约束或工程。实时 PC 收发尚待 A/C 确认协议，确认项见 `docs/成员A_PC收发协议确认清单_2026-10-03.md`。

## 取数位置

在共享仓库的 `member-a` 分支取数。原冻结标签 `member-a-v1.0.1` 不变；本次是视频测试数据扩展，不是重新训练或重新量化。

| 用途 | 文件 |
| --- | --- |
| 初次检查，两幅明显不同画面 | `artifacts/multiframe/two_frame_manifest.json`，frame 000 与 007 |
| 任务书 A1：旧权威帧 0000＋新帧 0001 | `artifacts/authority_pair/manifest.json`、`artifacts/member_a_authority_plus_second_frame.zip`；新帧来自视频 frame 007 |
| 固定 8 帧序列，按清单顺序处理 | `artifacts/multiframe/manifest.json`，frame 000～007 |
| 输入 | `frame_NNN_input_y_u8.bin`，每帧 518,400 字节 |
| 整数 Golden | `frame_NNN_output_y_u8.bin`，每帧 2,073,600 字节 |
| 输入缩略图 | `artifacts/multiframe/input_contact_sheet.png` |
| 软件参考预览，不是板上图像 | `artifacts/multiframe/software_golden_preview.gif` |
| 重算检查记录 | `artifacts/multiframe/verification.json` |
| 便携交接包 | `artifacts/member_a_two_frame_check.zip`、`artifacts/member_a_video_8frames.zip` |

原始 `.bin` 无文件头，单通道 uint8 Y，HWC 行优先；不含 RGB、音频、时间戳或串口协议头。输入 `960×540`，输出 `1920×1080`。PixelShuffle 通道顺序为左上、右上、左下、右下。每帧作为独立网络输入，卷积边界补整数零；不能把不同帧拼成一幅图送入网络。

ZIP 是便携取数/回传比对包，不含完整 PyTorch 推理环境。两帧包中的默认 `manifest.json` 只列 `[0,7]`；8 帧包的默认清单列完整序列。重新生成 Golden 需 clone A 源码仓库，并使用冻结标签中的 `artifacts/quant/`；不要仅凭 ZIP 运行训练/重算命令。

清单记录 frame ID、顺序、源视频帧号及时间、字节数、CRC32、SHA-256、全部整数层摘要，以及冻结 checkpoint、量化参数和权重包的来源。大尺寸逐层张量不重复入库；定位逐层问题时仍使用原有 96×54 向量。

## C 侧建议步骤

1. 先用 frame 000 和 007 分别跑一帧，检查结果确实随输入变化。两帧模式的清单顺序是 `[0,7]`，不要当成 `[0,1]`。
2. 两帧通过后再按 `[0,1,2,3,4,5,6,7]` 跑完整序列，电脑保存每帧原始回传数据。
3. 所有帧逐字节通过后，再导出电脑端播放预览和板级日志。

可以沿用已有 100 MHz 板测路径，不必等待高频优化。具体输入加载方式、帧启动、背压和 UART 帧边界由 B/C 确认；A 的清单编号不是新增硬件协议。若继续使用无帧头 UART，应在约定的完整帧起点之前开始采集；发现旧数据应保存并停止，不能清空缓冲区后假装边界正确。按固定帧长分段不能证明线上 frame ID 或 CRC 正确。

## 电脑端比对

工具只需 Python 标准库；生成预览时另外需要 Pillow。以下命令从 A 仓库根目录运行。报告及预览示例均写入 D 盘。

单帧回传文件：

```powershell
python scripts/compare_board_sequence.py --capture-file 'D:\Codex File\dialogue file\board_capture\frame0.bin' --frame-id 0 --report 'D:\Codex File\dialogue file\board_capture\frame0_report.json'
```

两帧连续原始输出必须严格按 `[0,7]` 拼接，长度为 4,147,200 字节：

```powershell
python scripts/compare_board_sequence.py --manifest artifacts/multiframe/two_frame_manifest.json --stream 'D:\Codex File\dialogue file\board_capture\two_frames.bin'
```

8 帧文件模式：把回传文件命名为 `frame_000_output_y_u8.bin`～`frame_007_output_y_u8.bin`，放入专用回传目录，不混入输入 `.bin`。

```powershell
python scripts/compare_board_sequence.py --capture-dir 'D:\Codex File\dialogue file\board_capture\8frames' --report 'D:\Codex File\dialogue file\board_capture\comparison.json' --preview-dir 'D:\Codex File\dialogue file\board_capture\preview'
```

也可以用 `--stream` 读取连续 8 帧无头输出，总长度必须为 16,588,800 字节。不能把串口日志文字、帧头或其他调试字节直接混入数据。

工具输出每帧的长度、CRC32、SHA-256、失配字节数、缺少/多余字节数、首错字节位置及像素坐标，并提示是否与另一帧 Golden 完全相同。正确时退出码为 0，失配、缺文件、长度错误或清单校验失败时退出码为 1。错帧诊断根据回传内容推断，不声称测到了线上编号。

预览仅在全部选定帧 PASS 后生成：每帧完整 PNG 和缩小的 GIF。GIF 是展示附件，不替代原始字节验收，也不代表实际回传速度。

## 离线 PC 播放器

导出一个可以双击打开的 HTML 文件。该文件内含画面数据，使用本机 Chrome 或 Edge 播放即可，不需要网络，也不连接串口。播放器提供播放/暂停、逐帧切换、位置滑块、循环及 1:1 原图查看；展示速度可选 1/2/4/8 fps，与 FPGA 吞吐没有关系。

只看软件整数参考：

```powershell
python scripts/export_pc_player.py --output 'D:\Codex File\dialogue file\board_capture\software_reference_player.html'
```

加载回传文件，在同一页面对照输入、Golden 和回传输出：

```powershell
python scripts/export_pc_player.py --capture-dir 'D:\Codex File\dialogue file\board_capture\8frames' --output 'D:\Codex File\dialogue file\board_capture\capture_player.html'
```

也支持 `--stream` 读取无头连续输出，以及用 `--manifest` 选择两帧清单。工具先校验参考文件，再逐字节比对回传数据；页面显示整组判定和每帧的长度、哈希、失配与首错位置。失败数据仍可导出诊断页面，但命令返回退出码 1；长度不正确的帧不绘制，避免把残帧误当作完整图像。软件参考模式明确显示板测未验证。

ZIP 中也包含播放器导出脚本与模板，只需 Python 标准库。直接运行源代码模板不会加载图像，必须先运行导出脚本。

控制器逻辑回归可在源码仓库运行 `python scripts/verify_pc_player.py --node <Node解释器路径>`，结果位于 `artifacts/pc_player_logic_test.json`。该检查使用模拟 DOM，覆盖灰度到 RGBA 的逐像素转换、暂停/切帧/循环/速度、1:1 尺寸和错误状态；它不是实际浏览器视觉验收。实际浏览器检查因安全策略核验失败而尚未完成，详见 `docs/成员A任务核验_2026-10-03.md`。

用户已手动打开 D 盘的软件参考播放器并确认“可用”，记录为 `artifacts/pc_player_manual_acceptance.json`，绑定 HTML 的实际 SHA-256。自动浏览器检查仍未完成；手动确认只覆盖软件参考可用性，不是板卡回传验收。

## 使用真实接收清单

`compare_received_frames.py` 按清单记录的到达顺序检查，不排序修正数据。清单是 PC 文件层格式，不是线上通信协议。C 的接收程序可按以下格式导出；`operator_supplied_capture` 仅说明采集者提供文件，并不自动确认板测来源。

```json
{
  "schema": "member-a-received-frames-v1",
  "sequence_id": "bbb_clip_01",
  "frame_count": 1,
  "evidence_source": "operator_supplied_capture",
  "frames": [{
    "frame_id": 0, "order": 0, "path": "arrival_000.bin",
    "bytes": 2073600, "sha256": "填写实际接收文件的64位SHA256",
    "receive_status": "complete", "crc_result": "NOT_CHECKED",
    "protocol_frame_id_observed": false,
    "first_byte_utc": "2026-10-03T01:00:00+00:00",
    "last_byte_utc": "2026-10-03T01:00:23+00:00"
  }]
}
```

示例时间替换为实际记录：每帧首个有效载荷字节开始、最后一个有效载荷字节结束，时钟带时区。`order` 从 0 开始；帧 ID 若由 PC 人工分段赋值，保留 `protocol_frame_id_observed=false`。CRC 未实现填 `NOT_CHECKED`，不能虚填 `PASS`。状态可为 complete/incomplete/timeout/error，CRC 可为 PASS/FAIL/NOT_CHECKED。重复、未知、缺帧和乱序清单返回 FAIL。只检查部分帧时须选择明确的参考子集清单，不能称为完整序列通过。

```powershell
python scripts/compare_received_frames.py --manifest artifacts/multiframe/manifest.json --received-manifest 'D:\Codex File\dialogue file\board_capture\received_manifest.json' --report 'D:\Codex File\dialogue file\board_capture\received_comparison.json'
python scripts/export_pc_player.py --manifest artifacts/multiframe/manifest.json --received-manifest 'D:\Codex File\dialogue file\board_capture\received_manifest.json' --output 'D:\Codex File\dialogue file\board_capture\received_player.html'
```

播放器按实际收到的已知帧显示，可展示 FAIL 便于诊断；缺帧不补 Golden。没有可播放的帧或收到未知 ID 时拒绝导出，先查对拍报告。页面显示序列 ID、帧号、当前文件来源和对拍状态，播放速度不等于接收速度或核心吞吐。

执行总回归：`python scripts/verify_a_multiframe_tasks.py --node <Node解释器路径>`。逐项命令、退出码、开始时间、耗时和日志位置在 `results/multiframe/task_execution.json`。此入口不会重训、校准或改变冻结参数；它核验原权威帧、成对包和 8 帧，测试接收错误及播放器控制器，重建 ZIP，并运行 Python 测试。

## UART 接收及隔离实验

正式 C 工程仍只有 TX，A 的 `scripts/capture_raw_uart.py` 只接收不上传，详见 `成员A_UART接收工具_2026-10-03.md`。对已有单帧 ROM 工程使用 `artifacts/authority_pair/single_authority_manifest.json`；不要期待发送新输入能被接收。

用户随后提供了未提交、未板测的双向 SRTP 隔离原型约定。对应客户端单独位于 `experiments/member_a_uart_prototype_20261003/`，README 给出完整格式、运行条件和失败边界。输入按外部复位后的连续 ID 从 0 开始，因此先用旧权威帧/新帧成对清单 `[0,1]`，再用完整视频 `[0..7]`；视频子集 `[0,7]` 不满足这一实验约定，客户端会拒绝。

三份便携包均包含实验客户端，但这不代表协议已冻结或正式 C bitstream 已具备 RX。软件联测仅使用复制 Golden 的端点，未接实体串口；`uart_prototype_selftest.json` 保存头部字节示例、包哈希和联测结果。真实启用前仍要取得 C 原型源码/版本，确认 CRC 与输出边界，再采集不同的两帧及 8 帧实收证据。任何生成的板测报告必须用真实保存的输出，不得拿软件样例顶替。
