# 成员 A PC 收发协议确认清单

## 当前状态

用户在本轮明确回复：目前没有确认版双向 UART/UDP 协议。A4 的输入协议、CRC 与流控仍待确定，不将接收旧 UART 输出视为该条件已经满足。

截至本次检查，C 分支 `c-side-latest` 的提交为 `910e60e85fca5c869c311289cc8586b8cfb8fdb3`。已核对 `rtl/c_top.v` 与 `rtl/readback_ctrl.v`：顶层只有 UART TX，没有 UART RX；回读直接发送数据字节，没有线上 frame ID 或 CRC 封装。其文档未发布面向 PC 上传视频的多帧协议。现有板测是单帧结果；不能把 A 的文件编号当成硬件线上帧编号。

历史 100 MHz 板测报告记录 `921600 baud、8N1、COM3（C 本机）`。这些是已有单帧测试条件，不是下一阶段双向多帧协议；PC 工具不能照搬 COM3，也不能假定向这条 TX 通路写入输入帧就会被 FPGA 接收。来源：[C 单帧板测报告](https://github.com/CalmDown789/a_dui_dui_dui/blob/910e60e85fca5c869c311289cc8586b8cfb8fdb3/report/c_board_100mhz/BOARD_TEST_REPORT_2026-09-24.md)。

A 的不同帧整数 Golden、8 帧预录序列、离线对拍工具和播放器可先供 C 使用。正式 PC 上传/回传适配要在 C 确认以下项目后启用。隔离实验不替代正式接口，也不要求 B/C 根据未经确认的格式改 RTL。

## 用户提供的隔离原型及 A 实验工具

用户补充了一份尚未提交、未板测的 C 双向 UART 隔离原型说明：921600/8N1；输入 `SRTP` 后接小端 uint32 帧号、长度、负载 CRC、头部 CRC；头部 CRC 覆盖前三个字段的 12 字节；负载为行优先 uint8 Y；先外部复位、帧号从 0 开始，逐帧 stop-and-wait。输出固定长度裸 Y，没有输出帧号、CRC、ACK、状态查询或软件复位。原文只位于另一台机器，当前没有可校验的源码提交。

A 的实现隔离在 `experiments/member_a_uart_prototype_20261003/`，只按用户明确给出的原型字段编写，不写入正式接口。IEEE CRC-32 使用 ISO-HDLC 全参数，仍须 C 用同一字节示例确认。软件测试提供旧权威帧与新帧的 20 字节头部、完整包 SHA-256，见 `artifacts/uart_prototype_selftest.json`；该文件明确标为软件样例，不是 C 接收成功记录。

客户端可保存输入包、写请求/已接受字节、原始输出、接收清单、逐字节报告，并复用同一播放器。输出 ID 是主机绑定值，不是线上观察值；输出 CRC 状态是 NOT_CHECKED。超时/多余数据停止会话、要求外部复位，不自动重发。工具未打开实体端口，不能作为协议确认或板测 PASS。只有取得相匹配的 RX 原型及板卡配置后才能实用，不得对正式 TX-only bitstream 发送输入。UDP 没有确认格式或实现。

裸输出仅串行传输就需要 22.5 秒/帧，输入加输出约 28.125 秒/帧（未计头部、计算和等待）；此路径适合低速逐帧验证，不满足实时视频收发。上述实验事实不改变下表正式协议的未确认状态。

## 收发适配的完成门槛

1. 协议版本及字节示例得到 A/C 明确确认，并绑定 C 的来源提交。
2. PC 正确处理部分读/写、长停顿和总超时；不得把一次串口 `read()` 当作完整帧。
3. 接收端校验长度、线上 frame ID 和校验字段，保存原始传输记录及剥离后的 Y 文件。
4. 用模拟传输覆盖正常、短读、截断、错误 CRC、重复/乱序、超时和恢复；再由 C 用真实板卡跑两帧与 8 帧。
5. PC 逐字节对拍和播放器使用同一份保存的输出；分别报告传输用时、完整数据帧数和数值判定，不从播放器展示速度推断 FPGA 帧率。

已增加与现有 TX 无头字节流配套的 PC 接收保存工具，见 `成员A_UART接收工具_2026-10-03.md`。它不向 FPGA 发送输入或命令；帧 ID 是主机按顺序赋值，无线上 CRC 可校验，文件 CRC 仅用于文件完整性。只有软件读取器验证，不是实体串口实测，也不是 A4 双向协议适配。另有上述原型实验客户端；协议、完整实时收发和新序列板测仍不能在总验收中写成 PASS。
