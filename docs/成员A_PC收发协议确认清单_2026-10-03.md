# 成员 A PC 收发协议确认清单

## 当前状态

截至本次检查，C 分支 `c-side-latest` 的提交为 `910e60e85fca5c869c311289cc8586b8cfb8fdb3`。已核对 `rtl/c_top.v` 与 `rtl/readback_ctrl.v`：顶层只有 UART TX，没有 UART RX；回读直接发送数据字节，没有线上 frame ID 或 CRC 封装。其文档未发布面向 PC 上传视频的多帧协议。现有板测是单帧结果；不能把 A 的文件编号当成硬件线上帧编号。

历史 100 MHz 板测报告记录 `921600 baud、8N1、COM3（C 本机）`。这些是已有单帧测试条件，不是下一阶段双向多帧协议；PC 工具不能照搬 COM3，也不能假定向这条 TX 通路写入输入帧就会被 FPGA 接收。来源：[C 单帧板测报告](https://github.com/CalmDown789/a_dui_dui_dui/blob/910e60e85fca5c869c311289cc8586b8cfb8fdb3/report/c_board_100mhz/BOARD_TEST_REPORT_2026-09-24.md)。

A 的不同帧整数 Golden、8 帧预录序列、离线对拍工具和播放器可先供 C 使用。PC 上传/回传适配要在 C 确认以下项目后实现。本文不指定帧头或命令字，不要求 B/C 根据未经确认的格式改 RTL。

## 请 A/C 确认的项目

| 项目 | 需要明确的内容 | 当前状态 |
| --- | --- | --- |
| 物理接口 | 输入/输出分别走 UART、USB FIFO、以太网还是其他接口；接口是否双向 | 未确认 |
| 串口参数（若适用） | 端口、波特率、数据位、校验、停止位、是否使用 RTS/CTS | 历史单帧为 921600/8N1；多帧参数未确认 |
| 会话与启动 | 如何复位、如何启动一帧、是否应答、何时允许发送下一帧 | 未确认 |
| 输入帧格式 | 无头定长还是带头；帧头、版本、长度、帧编号的位宽及字节序 | 未确认 |
| 输出帧格式 | 帧头、帧编号、长度、错误码；输出载荷是否就是 2,073,600 个 Y 字节 | 未确认 |
| 数据布局 | 960×540 Y 输入与 1920×1080 Y 输出；行优先；是否有条带或行填充 | A 数据规范已提供，线上格式待 C 确认 |
| 流控 | 主机分块大小、ACK/credit/ready 信号、最大待处理帧数、是否可收发交叠 | 未确认 |
| 校验 | CRC 的多项式、初值、反射、xorout、覆盖范围；是否有独立校验字段 | 未确认 |
| 异常恢复 | 超时、丢帧、截断、乱序时如何重同步；是否允许重发及如何去重 | 未确认 |
| 证据 | C 的协议文档提交、打包示例、正确/错误原始收发记录及版本 | 未提供 |

如果第一阶段仍使用 ROM 逐帧加载，C 只需确认每次启动与回传边界，A 可以先做接收保存及对拍；但这不等于 PC 上传视频通路已经实现。

## 收发适配的完成门槛

1. 协议版本及字节示例得到 A/C 明确确认，并绑定 C 的来源提交。
2. PC 正确处理部分读/写、长停顿和总超时；不得把一次串口 `read()` 当作完整帧。
3. 接收端校验长度、线上 frame ID 和校验字段，保存原始传输记录及剥离后的 Y 文件。
4. 用模拟传输覆盖正常、短读、截断、错误 CRC、重复/乱序、超时和恢复；再由 C 用真实板卡跑两帧与 8 帧。
5. PC 逐字节对拍和播放器使用同一份保存的输出；分别报告传输用时、完整数据帧数和数值判定，不从播放器展示速度推断 FPGA 帧率。

目前只有离线工具及数据的验证证据。协议、实时收发和新序列的板级回传未完成，不能在总验收中写成 PASS。
