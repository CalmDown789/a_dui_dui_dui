## PC 传输故障模拟

脚本 `experiments/member_a_uart_prototype_20261003/host/transport_simulator.py` 调用真实的 A 侧 PC 客户端，并以虚拟时钟和伪 UART 端点注入故障。默认使用 A 的权威帧+第二帧，不需要连接串口或 FPGA。

复现：

```powershell
python experiments/member_a_uart_prototype_20261003/host/transport_simulator.py `
  --manifest artifacts/authority_pair/manifest.json `
  --output-dir .data/pc_transport_simulator/run_01 `
  --summary artifacts/pc_transport_simulator_selftest.json
```

输出目录必须是新目录；脚本拒绝覆盖。验收脚本检查故障是否被正确检出：

| 场景 | 预期 |
|---|---|
| 正常短读/短写 | 完整收齐、逐字节 PASS |
| 延迟回传 | 在时限内完整收齐、逐字节 PASS |
| 少 1 字节截断 | 接收 FAIL，不向下一帧继续发送 |
| 回传相邻帧内容 | 长度可完整，但按预期帧逐字节比较 FAIL |
| 接收端帧号状态错位 | 接收端拒收且不回包；因原型无 ACK/状态字段，PC 最终报告超时而非解析出帧号错误 |
| 串口断开 | 保存已收部分，标记 FAIL，不自动重发 |
| 帧前残留数据（需外部复位） | 在发送首帧前停止，不猜测帧边界 |

该实验原型的输出是**无帧头裸 Y**，没有线上帧号、输出 CRC 或 ACK。因而“错帧”测试只能通过内容对拍发现错配，不能从线上输出字段识别帧号。该协议仍为 `PROTOTYPE_UNCONFIRMED`，正式 C 顶层只有 UART TX；不得把本模拟结果称为 A4 双向板测通过。

结果文件 `artifacts/pc_transport_simulator_selftest.json` 记录逐场景期望值、实测状态、虚拟耗时及每份原始会话目录。`.data/pc_transport_simulator/` 中的完整模拟流和接收文件不提交。

## 可修改的性能预算

脚本 `scripts/pc_performance_budget.py` 生成 JSON、CSV 和 Markdown，可通过命令行修改尺寸/倍率、帧率、像素格式、UART 波特率、以太网线速；也能读取已有接收会话拆分发送、等待、回传和本机对拍时间。用户实测的播放器耗时通过 `--playback-observed-seconds` 输入；未输入时只报告帧数/fps 的名义播放时间，不伪称实测。

生成当前预算：

```powershell
python scripts/pc_performance_budget.py `
  --width 960 --height 540 --scale 2 --fps 15,30,60 `
  --formats Y8,YUV420P,RGB24 --baud 921600 `
  --out-dir artifacts/pc_performance/current_run
```

分析已有客户端会话：

```powershell
python scripts/pc_performance_budget.py `
  --width 960 --height 540 --scale 2 --fps 30 `
  --session-dir 'D:\Codex File\dialogue file\board_capture\run_01' `
  --playback-observed-seconds 4.0 `
  --out-dir 'D:\Codex File\dialogue file\board_capture\run_01\performance'
```

当前配置 960×540→1920×1080、灰度 Y、30 fps 的下限预算：

| 项目 | 数值 |
|---|---:|
| 输入负载 | 518,400 B/帧；15.552 MB/s |
| 输出负载 | 2,073,600 B/帧；62.208 MB/s |
| 双向负载合计 | 77.760 MB/s；622.080 Mbit/s |
| UART 921600、8N1 输入发送 | 含 20 B 实验头约 5.6252 s/帧 |
| UART 输出回传 | 22.500 s/帧 |
| stop-and-wait 理想往返 | 至少 28.1252 s/帧，约 0.0356 fps；未计处理等待和软件间隔 |
| 一对输入/输出 Y 帧缓冲 | 2.592 MB；两对 5.184 MB；三对 7.776 MB |
| 全帧缓存读写模型 | 输入和输出各写一次、读一次：155.520 MB/s |
| 输出缓存写入+显示读取 | 124.416 MB/s |

DDR 项按整帧缓存一次写入、一次读取估算；纯流式/行缓存可少占外部 DDR。RGB24 HDMI 表格只计算活动像素，不包含消隐、TMDS 编码和链路开销。不得把上面算术结果当作 DDR MIG 实测、网络协议实现或板级实时帧率。

如有保存的 `received_manifest.json`，工具可报告发送时长、每帧首字节读回等待、首末载荷读返回跨度、总会话时间，并现场计时本机的逐字节对拍。接收时间戳是 PC `read()` 返回时间，不是 UART 引脚时间；首字节等待也不等同于 FPGA 纯计算时延。

## ACX750 视频接口资料核查

资料来源均为芯路恒/小梅哥公开支持页：

- [ACX750 用户自助服务手册：核心板/底板原理图、XDC、网表及器件说明](https://fpga.cn/forum.php?mod=viewthread&tid=29527)
- [ACX750 双目 OV5640→DDR3→HDMI 示例说明和工程入口](https://fpga.cn/forum.php?mod=viewthread&tid=29900)
- [OV5640 模组用户手册、模组原理图与传感器资料目录](https://fpga.cn/forum.php?mod=viewthread&tid=29331)

由厂商支持页可确认的参考信息：

| 模块 | 公开资料中的信息 | 对当前项目的意义 |
|---|---|---|
| FPGA | 200T 标注为 `XC7A200TFBG484-2` | 与本项目当前目标器件一致；仍须核对 C 使用的板卡丝印/修订版。 |
| DDR3 | 资料描述为两颗 x16 器件组成 32-bit 接口；给出实体器件 `F60C1A0004-M79W`、MIG 兼容器件 `MT41K256M16 RE-125` | 不能把兼容 MIG 型号误当成实装颗粒；训练、速度等级、位宽、bank/rank、时序和校准状态由 C 按实板 BOM/工程核对。 |
| CMOS 摄像头 DVP | D[7:0]、PCLK、HREF、VSYNC、XCLK、SCCB；支持页列出 3.3 V LVCMOS 约束和 SCCB 上拉 | 参考引脚见下表。具体 OV5640 模组版本、时钟、分辨率、输出格式与连接方向仍待确认。 |
| HDMI TX | 支持页列出 TMDS 时钟、D0–D2 差分对及 HPD/OE/SCL/SDA | 物理输出资源有公开映射；精确 IOSTANDARD、bank 电压、DDC 处理和时序必须按当前底板原理图/XDC 核对，不能仅从引脚列表推断。 |
| 示例 | 厂商列有双 OV5640 采集，经 DDR3 缓存，再由 HDMI 显示的 ACX750 示例 | 证明存在可查阅的参考工程方向；示例不等于已适配当前算法、板卡修订或 C 工程。 |

公开页面的 DVP 参考管脚：

| 信号 | FPGA package pin |
|---|---|
| `camera_data[7:0]` | `M16, M18, L18, L16, K16, K19, N20, M20`（按 `[7]` 至 `[0]`） |
| `camera_href`, `camera_pclk`, `camera_sclk`, `camera_sdat` | `N18, K18, J16, M17` |
| `camera_vsync`, `camera_xclk` | `N19, M15` |

公开页面的 HDMI TX 参考管脚：`HDMI_CLK_N/P=H19/J19`；`HDMI_D0_N/P=K22/K21`；`HDMI_D1_N/P=J21/J20`；`HDMI_D2_N/P=H22/J22`；控制信号 `HPD=N22, OE=M22, SCL=L20, SDA=L19`。这些是资料索引，不是可直接复制到当前 C XDC 的已验收约束。

共享仓库 `c-side-latest` 当前 HEAD `d6b13e625a15d952b6d3b657428472c1f51b1242`（2026-10-05 检查）仍是同一接口骨架：`constr/c_top.xdc` 顶层只有 50 MHz 时钟、复位、LED 和 UART TX；UART TX pin 仍待确认。`rtl/c_top.v`/`rtl/c_core.v` 是 ROM 输入和 UART 回传结构，没有摄像头采集、DDR MIG、HDMI TX 顶层端口。最新提交增加的是 B 证据补充文档/数据，不是视频外设 RTL。因此相机/DDR/HDMI 是**后续系统集成方向**，不是当前 A/B/C RTL 已经具备的链路。
