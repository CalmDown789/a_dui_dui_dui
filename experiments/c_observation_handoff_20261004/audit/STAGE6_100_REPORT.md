# Stage 6 fallback: fresh 100 MHz C-candidate implementation

Status: **FAIL_SETUP_TIMING**. The fallback candidate was freshly synthesized, placed, and fully routed with the complete C board constraints, but the restored-constraint setup result is negative. Vivado completed normally; no bitstream was generated and the board was not programmed.

The build used Vivado 2025.2 build 6299465, part `xc7a200tfbg484-2`, top `c_multiframe_synth_top`, fixed B source commit `6cc8ea4173d2a720f741e80b7cbd9279558ee93a`, the candidate C shell and observation logic, the complete C board XDC, and the generated ILA/VIO IP. The 50 MHz board input produced the checked 100 MHz MMCM clock (`g_mmcm.clkout_unbuf`, 10.000 ns period). This was a fresh source build, with 0.300 ns additional setup uncertainty during implementation; the final reports restore user setup uncertainty to 0.000 ns while retaining device jitter.

With the original uncertainty restored, setup WNS/TNS are **−3.790/−3293.397 ns**, with 2,862 failing setup endpoints. Hold WHS/THS are **+0.036/0 ns**, with no hold failures. All **107,622/107,622** routable nets completed with zero routing errors. Router verification succeeded. DRC found 1,145 warning checks and zero errors; NSTD-1 and UCIO-1 remained at Error severity and were not suppressed. `check_timing` reports zero registers without clocks and zero unconstrained internal endpoints. It separately lists two asynchronous inputs covered by the existing false paths and nine board outputs without output delays, as documented in the C XDC.

The worst setup path is within the encrypted `ila_obs_snapshot` IP. It has 118 logic levels (117 CARRY4 and one SRLC32E), with 13.179 ns data delay (12.613 ns logic, 0.566 ns route) against a 10.000 ns period. Internal names are masked, so the exact ILA operation responsible is not proven. A second repeated path is from the fixed B L5 `pending1_reg` to `win/shift_reg[*]/CE`: its net `win/E[0]` drives 6,406 loads and takes 12.089 ns of the 12.522 ns data delay in routing alone; slack is −2.754 ns. The routed clock reaches 87,891 loads. These reports identify both a debug-IP internal path and a substantial integration/fanout path in the B hierarchy.

The fixed-B comparison report shows this same L5 control is physically replicated in B's isolated `c_synth_top` route: `pending1_reg_replica_7` drove a 228-load net with 5.276 ns route delay, and its path met at +0.526 ns. The C candidate instead retained a 6,406-load net. Both checked implementations used the B route/place/phys-opt directives; the top hierarchy and integrated C loads/constraints differ. This supports an integration/physical-realization cause for the high-fanout path while leaving the exact reason for the replication difference open. See `audit/stage6_fanout_comparison.json`.

The +0.300 ns pressure report is 0.300 ns worse in WNS than the restored report, as expected. The final timing result is therefore not explained by an accidental period, uncertainty, or constraint-restoration error. The route completed successfully, so this is a design timing failure rather than a Vivado launch, license, or routing-process failure.
