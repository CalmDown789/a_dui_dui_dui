# Stage 6 timing failure: evidence and likely causes

## Confirmed result

The fresh 150 MHz candidate routed successfully but failed setup timing under the original C constraints: WNS/TNS `-6.984/-27871.592 ns`, with 33,451 failing setup endpoints. Hold was positive (`WHS +0.016 ns`, `THS 0`), pulse-width checks had +2.203 ns slack and no failing endpoints, all 107,867 routable nets completed, and the DRC report contained no Errors. Thus the immediate blocker is setup timing, not a route error or NSTD/UCIO pin DRC failure.

The 50 MHz `sys_clk` and generated `g_mmcm.clkout_unbuf` at 150 MHz are present. `check_timing_postroute.rpt` shows zero registers without clocks and zero unconstrained internal endpoints. It separately shows two asynchronous inputs without input delays but covered by the documented input false paths, and nine external outputs without output delay. These are not the internal setup paths reported as failing. The final clock report confirms the original user setup uncertainty of 0.000 ns. The +0.300 ns pressure report is exactly 0.300 ns worse in WNS, as expected; no timing relaxation or uncertainty deletion explains the negative result.

## Highest-confidence path contributors

1. The worst 150 MHz setup path starts and ends inside `c_multiframe_synth_top/ila_obs_snapshot`. Its data path is 13.191 ns, comprising 12.507 ns logic delay and 0.684 ns routing delay; it has 118 logic levels (117 CARRY4 and one SRLC32E). Vivado masks the encrypted IP's internal cell names, so the exact internal operation is not directly visible. The configured ILA has a 934-bit probe, 1024-sample depth, one match unit on that probe, and zero input pipeline stages. A very wide ILA trigger/match path is the leading explanation, but the report alone does not prove the exact comparator implementation.

2. Numerous next-worst paths start at `u_frame_loader/frame_start_reg` and end at high bits of 64-bit observer counters such as `u_observation/output_blocked_cycles_q_reg[53..63]`. These paths are about 12.1–12.3 ns, include 12–13 CARRY4 levels and a LUT2, and spend about 10.018 ns in routed delay. The source file confirms the observer uses 64-bit cycle counters. The wide increment/enable logic and frame-start control fanout are therefore another concrete timing contributor, separate from the masked ILA-internal worst path.

3. The 150 MHz candidate has 39,402 LUTs, 73,857 slice registers, 252 RAMB36, 10 RAMB18, and 394 DSP48E1. B's recommended `c_synth_top` result had 28,100 LUTs, 48,498 FFs, 226 RAMB36, 8 RAMB18, and the same 394 DSPs. The increase is consistent with the newly integrated C multi-frame/UART/observer/debug shell, rather than a change in the pinned B arithmetic source. The routed clock net reaches about 88,057 loads in the failing candidate, adding physical pressure.

## Why B's positive slack does not contradict this result

B's `route_setup030` used top `c_synth_top`; its worst path was the L5 FIFO write-pointer Q to a distributed-RAM write-address pin. The path was 6.033 ns, of which 5.654 ns was routing. This candidate uses `c_multiframe_synth_top`, adds the UART multi-frame receiver/loader and observation block, and includes a 934-bit ILA plus split-probe VIO. Its worst path is instead inside the ILA, followed by long observer-counter paths. Although the fixed B source closure, device, tool release, 150 MHz clock, and physical directives align, the complete designs are not timing-equivalent. B explicitly requires C to rebuild with its complete board XDC; its experiment margin is not a promise for this debug-instrumented C candidate.

The complete C XDC may affect placement through assigned package pins, but the timing report does not identify I/O paths as the failing endpoints. Current evidence therefore ranks ILA/observer logic and resulting clock/control fanout above the board pin constraints as the primary cause. Exact attribution of the masked ILA path remains open.

## Next evidence, without changing acceptance


The same candidate has now undergone a fresh 100 MHz source build. It also fails setup timing: restored-constraint WNS/TNS are `-3.790/-3293.397 ns`, with 2,862 failing endpoints. Hold is clean (`WHS +0.036 ns`, `THS 0`), and all 107,622 routable nets completed with zero route errors. The 100 MHz worst path is again inside the ILA and has the same 118 logic levels (117 CARRY4 and one SRLC32E), with 13.179 ns data delay against a 10.000 ns period. The exact operation inside encrypted ILA cells remains unknown. A second path in fixed B's L5 hierarchy runs from `pending1_reg` to `win/shift_reg[*]/CE`; the shared `win/E[0]` net has 6,406 loads and 12.089 ns route delay. This shows that reducing the clock from 150 to 100 MHz is not enough for this integrated candidate, and that the failure is not solely an ILA path.

The constraint checks support the design-timing diagnosis: the generated 100 MHz clock is exactly 10.000 ns, the original user setup uncertainty is restored to 0.000 ns (automatic device jitter remains), zero internal endpoints are unconstrained, and the +0.300 ns pressure result is exactly 0.300 ns worse than the restored result. Vivado returned exit code 0 after route, timing, route-status, DRC, and checkpoint generation. There are zero routing errors and zero DRC errors. Thus local tool execution is working; the candidate itself misses setup timing.

The likely contributors are now ranked as follows:

1. **ILA internal path — strongest direct evidence.** At both 100 and 150 MHz the single worst path begins and ends inside `ila_obs_snapshot`, and both reports show 117 cascaded CARRY4 elements plus one SRLC32E. The ILA samples a 934-bit probe at depth 1024 with one match unit and no input pipeline. A wide trigger/match path is plausible, but the encrypted cell names prevent proof of the exact function. The reports establish the path location and structure, not which ILA setting created it.
2. **Large fixed-B control fanout in the integrated C top — strongest additional 100 MHz evidence.** A B L5 `pending1_reg` drives a `win/E[0]` net with 6,406 loads. This path is dominated by 12.089 ns of routed delay and has `-2.754 ns` slack at 100 MHz. A read-only comparison found the exact same B source hash in B's isolated route report: there, physical optimization created `pending1_reg_replica_7`, whose control net had 228 loads and a 5.276 ns route delay; the path met at +0.526 ns. Both flows use `ExtraNetDelay_high`, `AggressiveExplore`, and `NoTimingRelaxation` in the compared experiment, while the candidate has a different top, complete C board constraints, UART/frame shell, observation logic, and ILA/VIO. This is direct evidence that the B high-fanout structure's physical realization differs in the integrated design. It is not evidence that B source changed or that Vivado failed; the precise integration factor that prevented comparable replication remains unisolated. See `stage6_fanout_comparison.json`.
3. **C observer counters and clock/control loading at 150 MHz.** The 150 MHz report also contains many near-worst paths from frame-start control to high bits of the 64-bit observer counters, with long carry chains and large route delay. The candidate's BUFG clock net has about 88k loads. The full C candidate uses substantially more logic and registers than the isolated B implementation.

B's reproduced 150 MHz `c_synth_top` result remains valid for that top and its constraints: WNS is `+0.492 ns`, route errors are zero. It does not certify the different `c_multiframe_synth_top` that adds UART receive/frame loading, observation counters, ILA/VIO, and the complete C board shell. The user's earlier image of a C 100 MHz positive result used Vivado 2022.2 and does not identify enough build inputs to prove it is the same top, netlist, constraints, or debug configuration as this fresh 2025.2 candidate. A tool-version contribution cannot be ruled out without a same-source, same-XDC cross-version rebuild, but current evidence does not indicate a local Vivado execution fault.

Do not alter the C XDC, downgrade DRC severities, or change B RTL to make either failing report pass.
