## 1. 接收核验（不需要板卡）

在两份ZIP所在目录，用实际Python 3.12路径代替下例：

```powershell
$taskPython = 'C:\Python312\python.exe'
& $taskPython -B .\C_TO_B_LATENCY_HANDOFF_V2_20261009\verify_delivery.py .\C_TO_B_LATENCY_HANDOFF_V2_20261009.zip
& $taskPython -B .\C_TO_B_LATENCY_HANDOFF_V2_20261009\verify_delivery.py .\C_TO_B_LATENCY_EVIDENCE_512_20261009.zip
```

需先解压工作ZIP以获取校验器，也可从交接人处单独取得。校验器不需要第三方库。证据ZIP含完整32个case，实际输出512份共1,061,683,200字节，报文journal约1.49 GB。证据包仅排除自动生成的`.Xil`与`__pycache__`，原始失败/恢复/清理记录保留。

## 2. 移机离线复核512帧

两份ZIP解压后，把工作包根路径记为`$taskRoot`，证据包解压根路径记为`$taskEvidence`。可独立放置。例如：

```powershell
$taskRoot = 'C:\b26\C_TO_B_LATENCY_HANDOFF_V2_20261009'
$taskEvidence = 'C:\b26\C_TO_B_LATENCY_EVIDENCE_512_20261009'
& $taskPython -B "$taskRoot\tools\audit_evidence.py" --evidence-root $taskEvidence --out-dir 'C:\b26\reaudit_01'
```

工具默认逐个调用`runtime/main/lab/audit_streaming_run.py`，重新核验源码/BIT/输入/Golden绑定、实际UART/JTAG顺序、协议CRC、输入完整性、proof及释放顺序、每帧输出和Golden。输出目录必须不存在，保留每个case的审计和日志。可以用`--case cases/io_timing/r0_0_timeout_full`只复核一个case。离线审计无需pyserial，完整运行入口需要pyserial。

## 3. 上板复现当前冻结方案

Python 3.12 + pyserial，Vivado 2025.2；PC4K的OpenCV/numpy/Pillow/Tk依赖仅涉及历史PC4K入口，不是本次LAB依赖。

```powershell
& "$taskRoot\runtime\main\run_integrated.ps1" -Mode Preflight -Python $taskPython -Vivado 'E:\AMDTools2025\2025.2\Vivado\bin\vivado.bat'
& "$taskRoot\runtime\main\run_integrated.ps1" -Mode Run -Python $taskPython -Vivado 'E:\AMDTools2025\2025.2\Vivado\bin\vivado.bat' -HardwareServer 'E:\AMDTools2025\2025.2\Vivado\bin\unwrapped\win64.o\hw_server.exe'
```

Preflight只检查本地文件，不使用UART/JTAG/网络。Run会RAM JTAG加载当前BIT，顺序执行Smoke/Probe/Natural2/Natural16并独立审计，结果写新的`runtime/main/attempts`目录。该入口重现冻结默认值，并不会自动采用实验batch1。新板卡/网卡与当前实际身份不同会被守卫拒绝；应明确发行新的硬件绑定候选，不能删掉守卫绕过。

现有环境：

| 项目 | 已测机器值 |
| --- | --- |
| FPGA | xc7a200tfbg484-2，JTAG device xc7a200t_0，ID 13636093 |
| JTAG target | `*/Digilent/250520092545` |
| UART | COM3，CH9102；编程前先捕获，编程退出后检查实际PHY0 |
| 网卡 | Realtek USB GbE，1 Gbps，MAC 00-E0-4C-19-4B-88；当前ifIndex 10、名称以太网3，后两项可随环境改变 |
| 主机/板端 | 192.168.0.3/24:6102 → 192.168.0.2:5000；永久邻居00-0A-35-01-FE-C0 |
| hw_server | TCP3121；原运行器只清理自己创建且身份匹配的服务，已有服务保持 |

512帧实验的原launcher最后未确认关闭服务；随后按PID/程序路径/启动时刻和原日志确认所有权并关闭。原`CLEANUP.json`和补充`OWNED_SERVER_CLEANUP.json`均保留。不得把原finally的false读为目前仍占用硬件服务，也不得只删掉失败记录。

原512帧控制器、实验driver、分析脚本使用`C:\t6int09`/`C:\t6ab09`和本机工具绝对路径；它们是可审查的原始来源，不是移机后一键入口。若重跑完整A/B实验，在新候选中明确改路径、重新生成实验来源SHA，保持平衡顺序、16帧/轮、每case重新JTAG/UART、固定窗口和验证强度。旧实验清单不能继续绑定修改后的实验脚本。

## 4. 准备B的新RTL构建目录

```powershell
& $taskPython -B "$taskRoot\tools\prepare_build.py" --out-dir 'C:\bbuild01'
```

此工具只复制当前RTL/MEM/XDC/Tcl，在新目录生成`synthesis.tcl`和完整布局布线的`full_implementation.tcl`。前者来自实际整合的综合段，保留EVF2与原约束；后者来自实际完整构建脚本。生成的综合脚本先切目录后读源，不依赖旧incremental_reference。它还复制最后的refine脚本作为负时序时的历史参考。完整从源重新构建不保证复现同一BIT哈希或一次达到正时序；当前成功BIT经过额外route refine，日志保留。

可在生成目录内分阶段调用Vivado（本次交接整理没有执行此操作）：

```powershell
Set-Location 'C:\bbuild01'
& 'E:\AMDTools2025\2025.2\Vivado\bin\vivado.bat' -mode batch -source .\synthesis.tcl -log .\synthesis.log -journal .\synthesis.jou
& 'E:\AMDTools2025\2025.2\Vivado\bin\vivado.bat' -mode batch -source .\full_implementation.tcl -log .\full_implementation.log -journal .\full_implementation.jou
```

检查上一阶段退出码再进入下一阶段。不要从本包`rtl/rebuild_from_source_no_bit.tcl`的历史名称猜测它就是整合BIT的完整发行入口。修改后的新候选需要更新来源身份与软件绑定，包中原清单只认证当前源/BIT，不能用于认证B的新修改。

## 5. 历史PC4K如何使用

旧BIT SHA256：`81377cedf56706a2de904344a8684bdaffcd1e46f3ffa8e65da6a5e1ff584c0e`。旧版完整交付ZIP SHA256：`e3d018433f92835545c50080ef044c909eb9c6972048af4494a06caf2ec1b4f0`，2,611,384,419字节，原目录`output/C_TO_B_LATENCY_HANDOFF_20261009.zip`及分卷保留。

V2带了旧PC4K源、说明和统计，便于B分析消费者及跨帧接口。若需重跑原PC4K150帧，使用旧完整包内相互配对的main与pc4k；V2当前main不能直接替换它。新BIT的PC4K尚未重新发行配对与上板审计，移植代码不等于验证完成。
