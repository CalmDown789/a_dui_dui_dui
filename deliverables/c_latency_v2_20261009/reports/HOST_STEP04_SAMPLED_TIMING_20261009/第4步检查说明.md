# 第4步：低扰动计时模式及离线对照

状态：**独立主机候选及离线回归完成，暂停等待检查。** 本步不修改 RTL，没有上板、真实 socket 收发或网卡配置变更。

## 本步改动

修改 `main/streaming/` 下四个文件：`timing_diagnostics.py`、`streaming_client.py`、`binary_journal.py`、`nonblocking_io.py`。完整差异见 `sampled_timing_changes.patch`。

新增显式配置：

```python
StreamingClient(..., io_mode='nonblocking',
                timing_mode='sampled', timing_sample_every=16)
```

默认仍是完整诊断 `timing_mode='full'`；原收发模式默认值也保留。仅在本目录候选中实现，没有接入现有配对运行入口。

采样模式按每个细粒度 stage 独立选择第 1、17、33……次调用；可配置间隔 1～1024。未选中时跳过诊断 QPC、线程 CPU 时钟、detail 字典及统计堆处理，采样判断位于这些开销之前。不会在已经读取时钟、构建 detail 后才丢弃结果。

### 保留的完整记录

- 每一条 TX/RX 原始 journal 及其时间戳、来源、顺序、字节内容。
- 每帧 wall 分段、调用线程 CPU、Golden、唯一输出包、重复/拒绝包、proof 数和最终释放记录。
- 所有输入/控制/proof/整帧截止时间判断、would-block 和缓存限制。
- 日志块写入、flush/checkpoint，以及可读/可写等待的计时。这些低频阶段始终记录。
- 全量报文及协议结果计数。新增 RX 分类计数，能与“已记录 RX = 已分类 + 已预取未处理”逐项核对，包含失败前缀。

保持同步原始日志；没有新增日志线程、异步队列或省略 checkpoint。CRC、Golden、逐包 proof、回调接纳和最终释放判断继续保留。`exchange`、`hello`、`input_packets`、`transfer` 等关键方法相对第三步做 AST 身份核对；本步功能修改集中在计时和计数。

### 采样报告的解释

`count` 和细粒度 `wall_total_ns`/CPU 累计/分位数仅表示**实际计时样本**，不乘以 16 推算全量。新增 `observed_calls`、`recorded_samples`、`population_scope` 和 `profiling` 字段说明完整调用数及采样范围。

未采样的慢事件可能遗漏，样本 P95 不能当作真实全量 P95。需要定位罕见长尾时选择完整模式。帧级计时始终完整；采样模式关闭原 `receive_service_interval` 派生统计，避免把两个样本之间的间隔误标成逐包服务间隔。

## 已完成的验证

| 收发模式 | 计时模式 | 主机故障回归 | 128 窗口完整两帧回归 |
|---|---|---|---|
| timeout | full | 26 组达到预期 | 7 组通过 |
| nonblocking | full | 26 组达到预期 | 7 组通过 |
| timeout | sampled | 26 组达到预期 | 7 组通过 |
| nonblocking | sampled | 26 组达到预期 | 7 组通过 |

每组完整两帧检查 **4,147,200 字节冻结 Golden**，独立原始日志审计通过。错误 Golden、整帧 CRC 错误、日志故障、回调拒绝、无协商和无输出等失败用例均没有释放帧或产生正常 JOURNAL 成功记录。四种组合的全部运行，RX 分类计数与原始接收数/缓存数均核对一致。

两个计时模式各自通过 **21 组非阻塞调度/截止时间检查**及 **5 组小几何双帧写背压检查**。最终请求持续不可写时仍零释放、保留 ABORTED_CAPTURE。原有 6 组协议边界检查通过。

另有 **10 组采样/日志检查**：

- 64 次 stage 调用，完整模式执行 128 次诊断 wall 时钟和 128 次 CPU 时钟，采样模式各 8 次；detail 构建从 64 次降至 4 次，报文计数仍为 64。
- 各 stage 独立选择，覆盖间隔 1、2、16、1024；checkpoint 全量记录；最慢 K 条和零耗时分桶保持正确。
- 200 条带固定时间戳的原始日志，在 full/sampled 模式下**逐字节及 SHA 相同**；采样只改变计时记录，不改变原始捕获。
- 在未选中的 journal append 上注入短写，错误仍使日志进入失败状态，checkpoint 被拒绝，没有正常 JOURNAL，并保留失败前缀及未提交尾部。

## 性能对照

同一冻结前两帧、同一内存对端、非阻塞收发，6 轮交替顺序比较三种实现。各次使用独立 Python 进程导入对应源码，避免第三步基线误用第四步依赖。计时区间包括 hello 与两帧传输，结束后的 finalize/fsync 和独立审计不计入该区间，但都执行并验收。

| 实现 | 两帧 wall 中位耗时 | 细粒度计时样本数中位数 |
|---|---:|---:|
| 第三步完整诊断基线 | 135.27 ms | 21,822 |
| 第四步完整诊断 | 144.18 ms | 21,822.5 |
| 第四步每 16 次采样 | **117.25 ms** | **1,365** |

采样模式比本步完整模式减少约 **18.68%**，比第三步完整基线减少约 **13.32%**。本步完整模式新增观测/结果计数等工作，本轮比第三步完整基线慢约 **6.59%**；默认完整模式不会自动获得采样模式的收益。

调用线程 CPU 的两帧中位值分别为 140.625、140.625、117.1875 ms，受当前计时粒度影响；这个线程也执行内存对端。上述数据均包含夹具 CPU、完整日志和验证，未调用真实网络/WinSock select，不含板端 CNN、PC4K 和显示，**不能换算实际 fps，也不能证明真实主机线程已经满足 33.333 ms/帧预算**。

本轮仅确认低扰动路径在该离线工作负载下减少开销。真实 Windows 收发收益、输入反馈/信用扩窗、跨帧预取、RTL 综合和实现时序仍留待后续单独推进。
